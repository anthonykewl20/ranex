## Slice goal

One governed change in this repository is evaluated against a declared gate, and
the verdict is produced by code, recorded, and reproducible.

## Operational outcome

> A person or an agent runs one command against a change and gets a `PASS` or
> `FAIL` that names the rule that failed and the evidence that was missing —
> from recorded evidence, not from a model's opinion.

## Shape

```
change proposed (a commit in this repository)
  → CLI:          PYTHONPATH=src uv run python -m ranex.cli.main gate evaluate <ref> --approver <identity>
  → application:  gate controller loads ONE gate definition
  → domain rule:  absence blocks — a required claim with no evidence FAILS
  → persistence:  append-only evaluation record, subject-digest bound
  → observable:   PASS/FAIL on stdout naming the failing rule; non-zero exit
  → verification: unit + integration + replay tests, plus one real run
```

## In-scope behaviour

- One CLI entry point, one subcommand.
- Loading **one** gate definition from a **YAML catalog**, exactly as the tracer
  does today.
- One rule with required claim IDs.
- Evidence records for those claims.
- Verdict: `PASS` / `FAIL`, with the failing rule and missing claim named.
- One append-only evaluation record bound to the subject digest.
- Non-zero exit on `FAIL`.

## Explicitly excluded — none of this may be added mid-slice

Loading from `architecture/contracts/` (**see below**); a second gate; a second
rule type; fleet, workers or dispatch; worktree isolation; leases; queues, event
buses or upcasters; the readiness resolver; authenticated human-decision
records; capability scoring; the record-freshness product capability; plugins;
caching; generalization to a second repository; **installation as a required
merge blocker**.

### Why the compiled tree is excluded — `SPIKE-01`

The generated registry contains **no action-gate rules**. Its gate rows carry
`{gate_id, tier_id, required_result, evidence_role, freshness_rule,
bridge_rule_id, noncompensating}`. The kernel's `GateDefinition` needs
`{action, rules[{rule_id, enforcement, resolution, required_claim_ids}]}`.
Executed: three load attempts, all failed; five fields would have to be
invented.

So this slice loads from YAML and **explicitly does not claim** to have closed
the pipeline. Closing it requires deciding what the action gates *are* and
authoring them — a separate decision, deferred.

## Behavioural contracts

| # | Given | Then |
|---|---|---|
| BC-1 | A required claim with satisfying evidence | `PASS` |
| BC-2 | A required claim with **no** evidence | `FAIL`. Never a default, never a skip |
| BC-3 | Evidence bound to a different subject digest | `FAIL`, naming the mismatch. Not ignored |
| BC-4 | Identical inputs, two runs | Byte-identical verdict and record |
| BC-5 | Model access removed entirely | No verdict changes |
| BC-6 | Producer identity equals approver identity | `FAIL` |

## Sad paths — each needs an executed test

Missing evidence · stale evidence · wrong-subject evidence · malformed catalog ·
duplicate rule IDs · gate with no blocking rule · unreadable store · store write
fails mid-append · two concurrent evaluations · absolute path argument · path
traversal above the repository root · remote or second-repository target.

The last three implement `SLICE-LANE-007`; they are the enforcement of
"governs only this repository," which is otherwise only prose.

## Acceptance criteria

1. Every behavioural contract and every sad path has an executed, passing test.
2. The command **blocks a real change** in this repository — demonstrated, with
   the output recorded. A check only ever observed passing is not evidence.
3. Two runs over identical inputs produce byte-identical records.
4. Removing model access changes no verdict (`ASR-01`, `BC-5`).
5. `pyrefly` reports no new errors (`ADR-0018`; run from `scripts/architecture`).
6. Every recorded measurement carries its command **and working directory**.

## Test strategy

`ADR-0008` TDD: failing test first, recorded. Unit (domain rules) · integration
(store) · contract (catalog loading) · replay (journal determinism) · one
end-to-end run against a real commit.

## Observability

Each evaluation appends one record carrying subject digest, gate id, rule id,
verdict, evidence considered, and the reason for a failure. Nothing inferred;
nothing asserted by the party being evaluated.

## Rollback and failure containment

Governs only this repository; grants no authority; produces **no readiness
evidence** (`SLICE-LANE-008`, and every record carries
`subject_lane: PRE_READINESS_PRODUCT_SLICE`). Rollback is reverting the commits.
**Advisory in CI only** — promotion to a required check needs a separate ADR
(`SLICE-LANE-006`).

## Size

≤ 1,000 net added lines of product source excluding tests (`SLICE-LANE-001`).
Exceeding it ends the slice and requires re-acceptance rather than failing the
build.

## What this slice validates, and what it does not

**Validates:** `RISK-01`, the product thesis — from the day it lands, a change
here is gated by code rather than by prose an agent can reinterpret. Also the
"absence blocks" rule under contact with a real change, and exact-subject binding
against a real commit.

**Does not validate:** `RISK-02`. The compiled tree still has no runtime
consumer, and this slice does not give it one. Saying otherwise would be the
false-closure pattern this project keeps recording.
