# ranex.dev benchmarks page — integration contract

For the web agent (ranex-web). This file is the contract for consuming the
kernel dogfood benchmark artifacts. It is versioned with the artifacts, so a
change here travels with the data it describes.

## The artifacts (this directory)

| File | What it is | May be edited by hand? |
|---|---|---|
| `benchmark.html` | Self-contained reference page: inline SVG charts, no external JS/CSS/fonts/network. The canonical rendering of the data. | **NO** — generated output |
| `benchmarks.json` | Raw data, schema `ranex-dogfood-report-v1`. The single source of every number and claim. | **NO** — generated output |

Both are regenerated by one command from the kernel repo root:

    uv run --frozen python tools/dogfood/dogfood.py report

A scheduled automation regenerates them nightly at 2:00 AM (after the proof
loop). To change page copy, labels, or design: edit `tools/dogfood/report_site.py`
in the kernel repo and regenerate — never patch the outputs. The plain-language
wording (cheat attempts, metric labels, human-time comparisons) is single-sourced
in `report_site.py` (`CHEAT_ATTEMPTS`, `PLAIN_TIMINGS`, `human_time`) — mirror
those strings in the web repo verbatim or import them; do not invent variant
claims the kernel cannot regenerate.

## Data contract (`benchmarks.json`)

Schema field: `schema: "ranex-dogfood-report-v1"` — fail the build on any other
value. Fields:

- `git_head` — commit whose kernel produced the facts. Show it; it is the
  provenance stamp for every claim on the page.
- `environment` — `{python, implementation, machine, system, cpu_count, note}`.
  The note says timings are one-machine, non-deterministic. The page MUST
  render the environment next to any timing.
- `proof_board` — `{total, passed, by_area, findings_open}`. Deterministic
  facts. Render "N of N" from `passed`/`total` — never hardcode "32".
  `findings_open` is the list of open F-ids (the "do we hide our own flaws"
  section); render its length and the plain description from the kernel's
  `tools/dogfood/FINDINGS.md`.
- `timings` — list of `{id, area, label, unit, repeats, median, min, max,
  samples}` (milliseconds). Always render median WITH its min–max range and
  repeat count. The 6 ids currently shown on the reference page:
  `admission-200`, `verify-200`, `journal-append-2000`,
  `journal-verify-2000`, `evaluate-20claims-100calls`, `cli-cold-start`.
- `scaling` — `{journal-verify, journal-append}`: points `{rows, median_ms}`
  (append points convert to per-row by dividing). Line charts; verdicts
  ("straight line", "flat, as designed") are derived in `report_site.py` —
  reuse that logic, don't eyeball it.
- `ledger` — iteration history: `{iteration, git_head, scenarios, findings}`.

## Integrity fingerprint

The sha256 of the exact bytes of `benchmarks.json` is printed in the page
footer and must be rendered on the web page too. Rule: the page shows the
fingerprint of the data it was rendered from. If the web page's displayed
fingerprint ≠ sha256 of the `benchmarks.json` it consumed, the page is stale
or hand-edited — that is the visitor-verifiable honesty check. Never display
a fingerprint computed from anything other than the exact consumed bytes.

## Update flow

Nightly: kernel automation runs the proof loop, then regenerates both files
in the kernel repo. Nothing in the web repo changes until the sync script is
re-run and the web repo is committed/pushed (no CI yet — publishing is a
manual or separately-automated step).

So the full freshness chain is:

    nightly loop (kernel repo) -> benchmarks.json -> sync-benchmarks.ts
    -> commit + push web repo -> deploy

Staleness is always visible: page shows `git_head` + fingerprint of the data
it rendered. Do not fake freshness: if the data is from yesterday, showing
yesterday's `git_head` is correct behavior.

## Honesty rules (site-wide "honesty infrastructure", applied here)

- Deterministic facts (proof board counts, cheat-attempt outcomes) may be
  stated as facts — they are checked twice nightly.
- Timings are single-machine medians: always rendered WITH environment, range,
  and repeat count. Never compare two timing values across days as if they
  were facts.
- Every public number on the page comes from `benchmarks.json`. If a desired
  claim is not in the data, the fix is to add a benchmark in the kernel repo —
  not to type a number into the web repo.
