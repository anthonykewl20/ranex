## Why zero, stated as an argument rather than an observation

Four of the brief's own constraints converge on the same answer.

1. **"Do not remove code solely because it appears unused."** Every candidate
   for removal is inert *data* — contract rows and reference documents. Their
   only observable property is that nothing reads them. That is precisely the
   grounds the brief excludes.

2. **"Prefer small reversible changes."** Zero changes is the smallest and most
   reversible option available, and it is on the table only because the
   measurement came out this way.

3. **"Preserve the working Slice 0 governance and evidence kernel."** Every
   Hermes-referencing artifact in the tracked tree is *generated by* or
   *validated by* that kernel. `architecture/contracts/` is generator output;
   editing it by hand desynchronises the generator and trips the `drift` check.
   The correct way to remove a contract row is to change its source and
   regenerate — which is a governance change, not a cleanup.

4. **"Resume Slice 1 only after its dependency path is understood."** The
   dependency path is now understood and it is empty of Hermes. Understanding was
   the deliverable; removal was never the prerequisite.

## The removal that would be a mistake

Recorded explicitly because it is the plausible next move and it is wrong.

**Do not "clean up" `architecture/contracts/` by hand — but not for the reason
you would guess.** 43 of the 47 files are **generator output**; the `drift` job
regenerates and compares, and — as of the 2026-07-31 audit fix — now detects
untracked output files too, a hole open since the original workflow. A hand edit
either fails `drift` or is silently reverted on the next regeneration.

**Four are neither.** `generated-output-authority.json` records **9 immutable
hand-authored inputs** (`immutable_input_count: 9`), of which four live here:

```
architecture/contracts/legacy-test-layout-policy.json
architecture/contracts/legacy-test-layout-policy-v1.json
architecture/contracts/legacy-test-layout-records.json
architecture/contracts/legacy-test-layout-records-v1.json
```

These are **immutable inputs, not outputs** — editing them is not "fixing
generated data," it is mutating a baseline the generator reads. They are also
exactly the files a Hermes cleanup would target: `legacy-test-layout-policy.json`
and its `-v1` carry **545 `hermes` matches each**. **Do not touch them.**

The distinction is load-bearing for §1 of this sequence: the `ADR-0010`
projection cannot be retired by regenerating, because part of its source is a
hand-authored immutable input, not a derivation. Surfaced by the Codex Luna
sweep and verified against `generated-output-authority.json`.

For completeness: `generator_output_count: 294`, `validator_output_count: 1`,
`output_count: 295`. The single validator output is
`docs/architecture/assessments/validation-report.json` — the tracked file no CI
job diffs, which is what `RFC-0007` asks the owner to decide.

The correct path for any contract change is: change the source document →
regenerate → validate → commit both. That is a governance change with an ADR
trail, not cleanup.
